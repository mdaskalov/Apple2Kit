## The MOS6502 package

The CPU is the `MOS6502` package. It has its own git repository,
https://github.com/mdaskalov/MOS6502; its README covers the CPU.

Apple2Kit uses it as a **git** dependency
(`https://github.com/mdaskalov/MOS6502.git`, `from: "1.0.0"`), not as a
local package by path: Xcode opens a local package in one window only, so
two projects referring to the same folder can't both build. With a git
dependency, Xcode builds from its own checkout (DerivedData/…/SourcePackages).

To use a change to the CPU: push it (and tag a new version) on GitHub, then
in the app choose *File ▸ Packages ▸ Update to Latest Package Versions*
(or `swift package update` here). `Data/mos6502.sh` (headless runner)
clones the tag `$MOS6502_REF` (default `1.0.0`, or a branch such as `main`)
into `$TMPDIR`; set `MOS6502_PACKAGE` to a local working copy to compile
that instead, uncommitted changes included.

Things used here:

* `CPU6502(memory:)` takes a 64K flat `mem`.
* `ioPages[page] = true` sends that page's reads and writes to
  `ioRead`/`ioWrite`.
* `step()` runs one instruction, and `cycles` counts on. While an
  instruction reads or writes I/O, `cycles` is the cycle of that access,
  which `DiskII` uses for its timing.
* `reset()` goes through $FFFC.
* `step()` throws on a JAM opcode. The app pauses and says where.

## Apple2 and Apple2Machine

Two classes, one machine:

* `Apple2Machine` (Emulator/) is the hardware: the CPU and its 64K, the
  memory map and soft switches, the language card, the keyboard latch,
  the Disk II, the cards. It runs a number of cycles when asked
  (`run(cycles:)`) and knows nothing of time, sound or the UI. It is
  `nonisolated` and builds without the app (`Data/headless.sh`, the tests).
* `Apple2` (UI/) is what an app holds: an `Apple2Machine` (`machine`) run
  at the Apple's speed from the display's frames, its speaker played,
  files opened (security‑scoped URLs), a CPU stop turned into `message`,
  and a status for a UI (`drives`, `registers`, `speed`, `videoMode`).
  It's `@Observable`, so SwiftUI updates with that status.

They stay apart for three reasons. The hardware's state changes millions
of times a second, and `@Observable` would track every access (it would
all have to be `@ObservationIgnored`). The core must build without
AVFoundation, QuartzCore and Observation for the headless runner. And a
model is a different ROM and memory map, so switching models puts in a new
`Apple2Machine` (the disks move across), which something above it has to
hold.

`Apple2` forwards what an app needs (`press`, `type`, `print`, `cls`,
`screenText`, `Apple2.Model`, `Apple2.clock`); the rest is on `machine`.

## Isolation

The package's default actor isolation is the main actor (`Package.swift`:
`.defaultIsolation(MainActor.self)`, Swift 5 language mode). The core types
are declared `nonisolated` so they don't depend on it, and
`Data/headless.sh` compiles them as plain Swift. `Apple2` and the view
run everything on the main thread: the display link calls
`Apple2.frame(at:style:)`, which
runs the CPU and returns the picture. A frame of 17,030 cycles takes well
under a millisecond, so there's no need for a thread yet.

## The run loop

`ScreenNSView` (macOS) and `ScreenUIView` (iOS, tvOS, visionOS) have a
`CADisplayLink`; on watchOS a `TimelineView(.animation)` stands in. For each display
frame, `Apple2.frame(at:style:)`:

1. Adds the time since the last frame × 1,020,484 to `owed` (at most 0.1 s
   behind, fractions kept) and runs that many cycles (`Apple2Machine.run`); what
   ran, the last instruction's overrun included, is taken off `owed`, so
   the machine doesn't gain on the clock.
2. Plays the speaker's clicks of those cycles (**Sound**, below).
3. With *Fast Disk*, while a drive's motor turns, keeps running a frame's
   worth of cycles at a time for up to 12 ms of the Mac's time
   (`runAhead`). A disk loads 10‑50× faster, and the display keeps
   updating. Not while the speaker sounds (a stretch of sound goes on,
   below), unless muted: a click stops it, and from the next frame on the
   machine keeps the clock's time until the speaker has been silent for
   ¼ s. So a program that beeps right after loading, the motor still
   running down for its second, sounds as it should. (Before, that sound
   came chopped up and late, queued ahead of the sound after it. Muted,
   the clicks made running ahead are dropped.)
4. Every 6th frame refreshes the status (drives, registers, mode, speed
   measured over half a second).
5. Draws the screen (`Apple2Machine.screenImage`, 560 × 192 in the view's
   `Screen.Style`), which becomes the layer's contents, stretched to the
   view's 280:192 with nearest‑neighbour scaling.

**Sound** (Hardware.md, *The speaker*). Each frame, step 2:
`soundPlayer.play(machine.takeClicks(), upTo: cpu.cycles, quiet:, muted:)`.
`SpeakerStream` renders the clicks up to the machine's cycle, so a tune
keeps its time from frame to frame. Pausing ends the sound with the cone
settling. A new stretch drops what is still queued (the last one's
silence) and plays at once, after its lead. Resuming, restarting, muting
and unmuting drop what is queued.

`Apple2Machine.run(cycles:)` steps the CPU until the cycles are used up, feeding
typed keys in between (`type`). A JAM stops it: the model pauses and shows
the message.

## Inputs, disks and binaries

* Keys: `ScreenNSView.keyDown`/`keyUp` → `KeyMap.ascii` → `Apple2Machine.keyDown`/`keyUp`
  by key code, the Mac's repeats left out (the //e repeats itself); losing
  the focus lets every key go. The view
  takes the focus when it appears or is clicked. `ScreenUIView`:
  `pressesBegan`/`pressesEnded` (a hardware keyboard, the Siri Remote) the same way,
  taking only the presses that are Apple keys (⌘ shortcuts go on); the
  on‑screen keyboard through `UIKeyInput` (`insertText` → `type`,
  `deleteBackward` → ←) and a key bar (`inputAccessoryView`: esc, ctrl for
  the next key, arrows). It takes the focus at once when a hardware keyboard
  is there (`GCKeyboard.coalesced`), else on a tap.
* ⌥ left/right (`flagsChanged`, device bits $20/$40; UIKit: the alt keys'
  presses) → `Apple2Machine.gamePort.buttons[0/1]`.
* A game controller → the joystick, every frame (`readGameController`,
  Hardware.md "Game port").
* Disks: `insert(url or DiskImage, drive:, boot:)` (a security‑scoped URL is
  opened for the read); `diskFileData(drive:)` gives the image back with
  what was written, for the app to save. The app owns the panels and drops.
* Text: `print(_:atX:y:uppercased:cls:)` writes on text page 1
  (`Apple2Machine.print`): row `y` (0‑23, else nothing), from column `x` or
  centred, cut off at the row's ends; a character past ASCII as `?`;
  upper case on the ][ and ][+ unless `uppercased: false`; the page
  cleared first unless `cls: false`. `cls()` fills it with spaces. It shows
  while the screen is in text mode (as at power‑on).
* Binaries: `load(url, at:, run:)` / `load(bytes, at:, run:)`, as DOS's
  `BRUN`: the bytes into `cpu.mem` (up to $BFFF), then with `run` PC at the
  address, the machine otherwise as it is (no BASIC, nothing typed). On
  the stack goes a return to the monitor ($FF69 − 1), so a program ending
  in RTS lands at the `*` prompt. A machine that hasn't run yet (under
  ½ s) first runs the ROM's start‑up without booting a disk, so the
  screen and the I/O hooks (COUT at $36) are set up. The ROM stays in
  any case: programs call it, and the CPU's vectors are there. Without
  ROMs (`roms: .none`) there is no start‑up: memory stays as it is (text
  printed before shows), and an RTS at the end goes to $FF69, which is
  RAM. Without an
  address `load(url)` takes `#06XXXX` from the file's name
  (`loadAddress(in:)`, what `dsk.py extract` writes), else $0800.
* Model switch (][ ↔ ][+): a new `Apple2Machine` with the other ROM; the disks move
  across.

## The view

Two ways to make one:

* `Apple2View(apple, style:, scale:)`: the app holds the `Apple2`
  (`@State private var apple = Apple2(…)`) and sets it up itself, e.g. in
  `.task`; it can work it later (keys, disks, pause, the status).
* `Apple2View(model, roms:, style:, scale:) { apple in … }`: the view
  makes its own, in `@State`, when it first appears, and runs the setup
  closure on it once. It lives as long as the view. (An `Apple2` made in
  a view's `init` would be made again each time SwiftUI rebuilds the view.)

Either way the view puts a `ScreenNSView` in an
`NSViewRepresentable` (a `ScreenUIView` in a `UIViewRepresentable`; on
watchOS an `Image` redrawn by a `TimelineView`) with `.aspectRatio(280:192, .fit)`, and with a
`scale` a fixed frame of 280·scale × 192·scale points. Without one it fills
what it is given at the aspect ratio; the app decides the rest (background,
minimum size, window fitting). On a Retina display 1× shows the picture's
560 dots a row one pixel each. The style is the view's, so two views could
show one machine differently; but each view runs the emulator with its
display link, so show a machine in one view at a time.

## Headless runner

`Data/headless.sh` compiles `Data/headless.swift` with `Sources/Apple2Kit/Emulator/*.swift`
and the MOS6502 sources (`-O`), then runs a script of actions from the
command line: insert disks, power on, run N seconds, run until a text
appears, type, print the text screen, write a PNG, dump memory, save the
disk. It runs about 100× faster than real time. Use it to check a change
without the app:

```sh
cd Data
./headless.sh --disk dos33_master.dsk --power \
    --until 'GLAD TO MEET' 10 --type 'CATALOG\n' --run 1 --png /tmp/s.png
```

## Adding things

**128K //e, 80 columns.** The //e runs with 64K (Hardware.md, *The //e*).
For 80 columns (`PR#3`) and 128K software it needs aux memory (RAMRD,
RAMWRT, ALTZP, 80STORE with PAGE2/HIRES) and the 80‑column display (aux
and main bytes in turn, 560 dots), and Delete as $7F. Aux memory doesn't
fit a flat `mem`: either swap 48K banks into
`cpu.mem` when RAMRD/RAMWRT/ALTZP change, or make more pages I/O pages.
The CPU's `push`/`pull` use `mem` directly, so ALTZP needs the swap. The
enhanced //e needs a 65C02, which `MOS6502` doesn't do.

**`.woz` images.** They carry the bits of each track with their timing, for
copy‑protected originals. Replace the nibble array with a bit stream and
move the latch on by elapsed cycles / 4 bits.

**13‑sector disks** (DOS 3.2, `.d13`). These use 5‑and‑3 encoding and need
the 13‑sector boot ROM.

**A debugger.** The CPU can stop at addresses (`traps`/`onTrap`), and the
`MOS6502` package's `Opcode`/`AddressingMode` can disassemble
(`Opcode(byte).mnemonic`, `.mode`, `.length`). A breakpoint list and a
disassembly view at PC would be small additions.
